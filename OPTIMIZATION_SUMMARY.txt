================================================================================
                    FALCON TRAINING GPU OPTIMIZATION SUMMARY
================================================================================

PROBLEM IDENTIFIED:
-------------------
Current config (falcon_hm3d_train_mini_junwei.yaml):
  ✗ Only using 8GB / 32GB VRAM (25% memory utilization)
  ✗ GPU compute at <15% utilization
  ✗ Only using 1 of 2 available V100 GPUs
  ✗ Training takes ~20 hours for 800K steps

ROOT CAUSES:
------------
1. Small batch size (4 environments, 2 mini-batches)
2. Small model (ResNet18 + LSTM128)
3. CPU bottleneck (simulation slower than GPU inference)
4. Single GPU (not leveraging 2nd V100)
5. Single-threaded PyTorch

================================================================================
                              SOLUTION OVERVIEW
================================================================================

OPTIMIZATION STRATEGY:
----------------------
1. Increase parallel environments: 4 → 16
   → More samples per update, better GPU saturation

2. Upgrade model architecture:
   - Backbone: ResNet18 → ResNet50 (4x more compute)
   - LSTM: 128 → 512 hidden units (4x larger)
   → More compute = better GPU utilization

3. Increase batch size:
   - Mini-batches: 2 → 4
   - PPO epochs: 2 → 4
   → Larger batches = more efficient GPU processing

4. Enable distributed training (DD-PPO):
   - GPUs: 1 → 2
   - Each GPU handles 8 environments
   → 2x hardware parallelism

5. Enable multi-threading:
   - force_torch_single_threaded: True → False
   → Better CPU utilization

================================================================================
                            TECHNICAL DETAILS
================================================================================

WHY THESE CHANGES IMPROVE GPU UTILIZATION:
-------------------------------------------

1. More Environments (4→16):
   - Increases batch size for GPU operations
   - Reduces GPU idle time waiting for CPU simulation
   - Better amortizes kernel launch overhead

2. Larger Model (ResNet18→50, LSTM128→512):
   - More compute per forward/backward pass
   - Better utilizes GPU's massive parallelism
   - Increases memory bandwidth usage

3. Larger Batches (mini_batch 2→4, epoch 2→4):
   - More efficient GPU memory access patterns
   - Better utilizes tensor cores on V100
   - Reduces overhead from small batch operations

4. Multi-GPU (DD-PPO):
   - Distributes environments across GPUs
   - Each GPU processes independently
   - Gradients synchronized via fast NCCL backend

5. Multi-Threading:
   - Allows PyTorch to parallelize CPU operations
   - Better overlap of CPU preprocessing and GPU compute
   - Reduces CPU bottleneck

MEMORY BREAKDOWN (per GPU):
---------------------------
Model parameters:
  ResNet50:        ~25M params × 4 bytes = 100 MB
  LSTM512:         ~2M params × 4 bytes = 8 MB
  Total model:     ~110 MB

Optimizer state (Adam):
  2x model params for momentum/variance = 220 MB

Rollout buffer (8 envs × 128 steps):
  Observations:    ~500 MB
  Hidden states:   ~200 MB
  Actions/values:  ~50 MB
  Total buffer:    ~750 MB

Activations during training:
  Forward pass:    ~2 GB
  Backward pass:   ~4 GB
  Total:           ~6 GB

Auxiliary tasks:
  People counting, position, trajectory: ~1 GB

Habitat simulation overhead: ~20 GB

Total: ~28 GB per GPU
